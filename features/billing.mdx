## Where checkout runs

- **Website:** `https://kyrou.org`, on the Cloudflare Pages project `kyrou-landing`. `www.kyrou.org`
  redirects there.
- **Environments:** Pages Production talks to the production Worker, and PR preview deployments
  talk to the dev Worker. A checkout ticket only works on the Worker that created it.
- **Desktop app:** opens `https://kyrou.org` by default. A dev build pointed at the dev Worker must
  set `VITE_CHECKOUT_URL` to a preview deployment.
- **Support:** `support@kyrou.org`.

## What it does

Kyrou has no freemium tier. The flow is: download the app → onboarding → paywall → pay on the
website's own `/checkout` page (a Paddle.js overlay) → the app rechecks entitlement and unlocks.

Payment never happens inside the desktop app itself — only a link out to the website checkout and
a link out to Paddle's hosted customer portal for managing an existing subscription.

- `src/app/Paywall.tsx` — the paywall screen (not wired into boot)

## How it works

1. **Webhook.** Paddle posts subscription/customer events to `POST /v1/paddle/webhook`. The
   signature is verified with a hand-rolled HMAC-SHA256 check against every `h1` value in the
   `Paddle-Signature` header (covers secret rotation) — no `@paddle/paddle-node-sdk`, since a plain
   `crypto.subtle` check is smaller and runs natively on Workers. A bad signature always returns
   401, never a 2xx. Events upsert `billing_customers`/`billing_subscriptions`, guarded so a
   stale or replayed event (`occurred_at` older than what's stored) can never overwrite newer state.

2. **Entitlement.** `GET /v1/billing/entitlement` joins subscriptions to customers on the **signed-in
   user's JWT email claim**, not the `user_id` the webhook wrote from checkout's `customData` —
   that field is set client-side during checkout and isn't trustworthy for authorization on its
   own. `grantsAccess(status)` treats `active`, `trialing`, and `past_due` as entitled; `paused` and
   `canceled` are not. A subscription with a scheduled cancellation still grants access until it
   actually lapses.

3. **Portal.** `POST /v1/billing/portal` resolves the Paddle customer the same way (JWT email) and
   returns a hosted customer-portal URL, which Settings opens externally.

4. **Client gate.** `needsPaywall(apiUrl, token)` calls the entitlement endpoint and **fails open**
   on any error (including offline) — a network hiccup can never lock out a user who has already
   paid.

## Known gaps

- The paywall screen is not shown anywhere yet; nothing in the app calls `needsPaywall()`.
- Only the dev database and dev Paddle sandbox are wired up. Production secrets and the
  `0010_billing.sql` migration on the production branch are still pending.
- A user who pays with a different email than the one they sign into Kyrou with is never entitled,
  because entitlement is bound to the JWT email. There is no account-linking flow yet.
